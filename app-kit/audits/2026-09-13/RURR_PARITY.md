# app-kit audit: fixed rurr feature and functional parity

Audit date: 2026-09-13. This is a source/specification comparison, not a successful runtime, performance, compatibility, or strict-live certification. No source, vendor, or historical planning files were changed for this sub-audit.

## Conclusion

**Full feature and functional parity with the vendored rurr package is not implemented, and the current app-kit specifications deliberately forbid several capabilities necessary to achieve it.** Completing the existing implementation against its current 20-type/22-method contract cannot meet the user's expanded parity target. The next work must include a normative specification amendment, followed by implementation and an executable parity matrix. This is a scope conflict, not merely an unfinished-code problem.

The existing app engine has substantial app-native capabilities: versioned declarative graphs, exact Agent and StateStore composition, per-node agent selection, state mutations, ordered conditional/broadcast routing, input interactions, children/maps, joins, durable checkpoints/recovery, cancellation, and unknown-effect handling. Those are meaningful implementation observations and contract commitments. They do not establish parity with rurr's whole application/action/state/streaming/tracking/operations ecosystem.

## Specification extensions required before implementation

1. **Parity charter and acceptance matrix.** Replace "equivalent required outcomes remain available" (`RESEARCH.md:73-75`) with an exhaustive adopted/different/excluded/unimplemented matrix. Snapshot polling cannot represent every stream item, fork a past checkpoint, pause before any node, or recover deleted logs. Pin the rurr commit/hash and distinguish runtime-core parity, behavioral parity, wire/storage compatibility, and full tooling-package parity. Record each intentionally omitted ergonomic or integration feature explicitly.
2. **Action execution and input/output model.** Current app authorizes a closed step vocabulary, with Agent as the sole general external execution seam. Full rurr parity requires ordinary executable work beyond agents, separate runtime inputs/state/results, read/write contracts, deterministic output validation, dispatch acceptance and cancellation/retry safety. Define the minimal legal seam and amend root trait constraints if needed. This is central to loosely coupled agents, tools, storage, and workflows.
3. **State/expression semantics.** Define complete operator tables, numeric domains, float handling, division/modulo, comparison equality, missing versus null, membership type errors, static and runtime typing, nested path access, reducer base handling and collision order. Current schema names are not a complete semantic contract.
4. **Control and streaming.** Define step/halt/pause/continue independently of input and cancel; selector/tag validity; transient payload versus committed snapshot; bounded subscriber delivery, backpressure, reconnect/replay, at-least-once/at-most-once semantics, and drop behavior. Add a lower Agent contract proposal if token-level prompt streaming is required.
5. **History, fork, and retention.** Define when results remain accessible after handle drop; minimum/configurable retention, terminal lookup behavior, source pins and fork lineage, exact checkpoint restore, definition revisions, safe state overrides and external-effect reuse. Current private 1-second terminal retention is too weakly specified for a production debugging/history requirement.
6. **Child composition.** Specify static versus dynamic subgraphs, recursive graph policy, task inputs and sources, graph/state fan-out, sequential pipeline semantics, empty/error results, canonical ordering, inherited versus overridden child policy, and distributed/external executor responsibilities. Keep lower construction and backend credentials outside app.
7. **Observability and operations ownership.** Separate metadata-only tracing from durable tracking, content capture, S3/file compatibility, API/UI queries, annotations, CLI operations, and exporter lifecycle. Current specifications deliberately prohibit many of these; decide host/caller versus app responsibility and document a bounded permission model if content is captured.
8. **Compatibility proof.** Every retained behavior needs an app public test mapped to exact rurr behavior, not a prose resemblance. Use deterministic source-local cases for expressions/routing/results and strict-live for real service/persistence/process claims; include crash/ambiguous-receipt scenarios for app's stronger durability.

## Recommended implementation order

1. Approve an app-kit specification amendment that resolves the new full-parity requirement against deleted surfaces and root ownership constraints. No production implementation should expand the allowlist ahead of that amendment.
2. Complete all current-contract correctness work found by the parallel source and validation audits. Retain exact static lower composition and durable effect/cancellation semantics.
3. Add an executable parity ledger, initially marking missing capabilities truthfully. Introduce state/expression and input/output semantics first, since later controls, streaming and child execution depend on them.
4. Implement adopted action/control/streaming and history/fork capabilities with owning tests; then adopted child/executor composition and tracking/operator functionality. Preserve app control-plane schema isolation from Burr files.
5. Complete `app-kit/docs/` with runnable multi-agent examples and the operational guarantees actually validated. Include backend feature wiring through storage-kit and caller-owned agent reopen, not hidden lower construction.
6. Run documented app/workspace gates and genuine strict-live tests. The agreed completion target is met only when its capability rows are implemented. User-accepted exceptions revise that target and must be reported as explicit limitations; they do not establish full feature or functional parity.

## Proof limits

This sub-audit read fixed archive members and current app public/spec/source boundaries. It did not execute rurr, extract the archive, modify production, inspect immutable `tmp/**`, or claim tests passed. The parent audit owns actual validation outcomes. All alleged full-parity completions must distinguish specification text, source observation, executable evidence, and strict-live evidence.
