# Independent design review: rurr core step/history/fork and App BSP

Read-only review, 2026-09-13. Scope: core execution, action sequence, retained checkpoint history, resume/fork, multiple BSP controls, terminal results, crash recovery. Server/UI/CLI and external observability integration remain excluded. No Cargo or source changes were made. Vendored evidence was read with `unzip -p app-sdk/vendor/rurr-main.zip <member>`; archive identity is the already-verified audit SHA `5b5f20eb1d233467c600dc9dd249feaaa9046c5a303ae4e937040be5b6ecf25e` / commit `005bfe3ece631e64b06dac2d42ef84235f727a4f`.

## Decisions recommended for the completion plan

1. **One engine and one durable mutation path.** Keep App's BSP execution as an app-native extension; preserve exact rurr behavior on the serial first-match/action graph subset. Do not add a second serial compatibility engine. A single-step call advances one committed execution boundary: one action in a serial graph, a canonical ready wave for broadcast/BSP graphs. Public output must explicitly represent the wave's action outcomes; it must never call a staged contribution committed state. Compare the single-action projection against rurr. This is an honest extension definition, not a claim that rurr defines BSP stepping.

2. **Separate action position from persistence fencing.** Existing `CheckpointRecord.sequence` (`app-sdk/src/workflow/run/mod.rs:55-63`) counts every durable control, intent, notification and cancellation update. It cannot serve as rurr's per-action `__SEQUENCE_ID`. Keep the current monotonic control/checkpoint identity for concurrency; add an action ordinal and action position to execution-boundary metadata. First rurr action ordinal is zero. An intent, input resolution, retry timer or repeated notification must not pretend an additional action committed. Action attempt identities and operation receipts stay separate from user action ordinal. For BSP, allocate unique action ordinals canonically from ready-set order and expose that explicit order, not completion timing.

3. **Retain immutable history rows and a mutable head.** Extend existing `RecordKey`, closed `AppMutation` and `AppStore` codec/receipt path. Store bounded immutable checkpoint records keyed by run and unique control sequence, with semantic kind (initial/control/action boundary/terminal), action ordinal/position, committed state, frontier and sufficient recovery facts. The run head references the current checkpoint; loaded runtime materializes the current record without a second authoritative copy. Remove `RunRecord.previous: Option<CheckpointRecord>` after predecessor lookup uses the immutable row. Do not keep both inline current+previous state and an independent full-history copy permanently.

4. **Checkpoint selection and action-sequence selection are distinct.** Inspecting an exact checkpoint is direct lookup; selecting rurr-style action ordinal uses an App-owned index/projection of execution-boundary records, not `StateRevision`. Failure/retry can share an attempted action ordinal before a commit, so row identity is the monotonic checkpoint sequence and action metadata determines projection. Exact ordinal lookup needs specified latest matching observation ordering, derived from monotonic App sequence rather than wall-clock guesses. Default missing target is an error for an explicitly requested App historical checkpoint; any rurr initializer-style fallback state/entrypoint must be a distinct explicit request option and tested, never a silent fallback.

5. **Default retained terminal results.** Delete one-second automatic deletion. Keep history and terminal result until the caller explicitly deletes the terminal run (or an explicitly configured retention policy authorizes deletion). Prefer one terminal-run deletion operation over an unrequested tuning family. This protects late observers and avoids a forest of receiver pin/retention tokens. Releasing active execution capacity at terminal cleanup must be separate from deleting retained history; otherwise `MAX_RUNS` will become a lifetime total-run quota. Retained rows must not all be loaded into memory on open. History is paged through existing CS list operations.

6. **Fork copies a closed, replayable boundary into a new run.** Use one request covering source selection, state override and resume position. Fork admission transactionally loads/fences the selected source checkpoint, validates source identity/definition/workspace pins, creates the new run and initial history row, reserves capacity and writes a receipt. The source remains unchanged. Copy the selected committed state into the fork so its future execution does not depend on the source staying retained; source pointer is lineage metadata. This eliminates durable fork pin graphs for normal completed boundaries. No lower handles, Agent IDs, provider continuations, credentials, native transactions or active notification identities are copied.

7. **Unknown is never reset by fork/rewind.** A current source run may be Unknown while an earlier clean completed checkpoint is selected; forking that earlier immutable checkpoint is a new user-authorized run and may deliberately execute subsequent effects again. Explicit source state/lineage makes that visible. A checkpoint containing an in-flight or Unknown effect is not a resumable fork boundary until its effect is resolved; reject it with a precise conflict. Do not silently turn it into a fresh undispatched attempt. Read-only inspection remains legal. Resume of the same existing run reattaches existing reservations and retains Unknown. A proven-safe failed action boundary can restart at its position under normal retry semantics; a failure after potentially accepted external dispatch stays Unknown, preserving App's stronger safety contract.

8. **Represent all sibling controls in the existing checkpoint owner.** Replace singleton `Option<ControlRecord>` in each lifecycle variant (`run/mod.rs:68-94`) with one bounded canonical map on CheckpointRecord keyed by activation/sequence; lifecycle phase remains a data-carrying enum. Avoid duplicating controls in Active/Failing/Cancelling variants. Use receiver methods to access/settle exact targets, not public runtime fields. Existing individual ControlRecord state enum remains the owner for input/attempt/sleep/child. Each sequential notification gets a distinct target generation within its attempt and durable settlement evidence; it must not reuse one OnceLock or the prior notification's resolution cell.

9. **Public snapshots must expose simultaneous actionable truth.** Existing singular `RunStatus::Waiting(Interaction)` and `Unknown { sequence,.. }` (`workflow/mod.rs:60-77`) cannot represent an input sibling and an unknown-agent sibling together. Reduce status to run lifecycle and expose one canonical list of actionable controls in RunSnapshot, extending the existing Interaction enum with Unknown information rather than adding parallel input/notification/unknown collection types. A target-specific resolution fence prevents settling control A from invalidating an independent pending control B; whole-checkpoint revision still fences cancellation and global state modifications. Define conflicting settlement versus duplicate retry explicitly. This is a coordinated signature/spec amendment, not an ad hoc compatibility overload.

10. **Controlled execution must share the existing driver.** One execution policy/mode enum on the run's driver state chooses automatic, pause-at-boundary or one-boundary advancement. Step/iteration must claim exclusive execution authority through the existing RunCell/generation; two separately reopened run handles must not compete. Read-only observers may coexist. Prefer a unique non-Clone execution session with one state enum and `next`/`finish` receivers over separate StepRunner/IteratorRunner/StreamRunner families. Lazy iteration validation occurs before first action/effect. Drop stops admission of later work; accepted work remains owned until cleanup and a durable pause/Unknown boundary. The owner must not detach async cleanup. A caller timeout ends observation, not native finalization authority.

## Pinned semantic evidence that changes simplistic designs

- `rurr-main/crates/rurr-core/src/application/api.rs:11-33`: step executes one action transactionally, returns None only when no next action; async counterpart has the same action semantics.
- `.../application/state_meta.rs:94-100`: absent sequence reserves 0; otherwise reserves last committed sequence+1. `.../application/step_txn.rs:62-79,95-127`: sequence enters working state; commit stamps sequence/prior action; rollback returns the exact start state. Do not increment user action count for App control-only checkpoints.
- `.../application/build/initializer.rs:237-261`: overrides are applied, loaded sequence is stamped, Completed sets prior action and continues after it, Failed resumes at its saved position, resume-at-next=false clears prior action. `:18-28` rejects explicit fork target with the same App id. `:183-210` preserves source identity as parent pointer while target has its own identity.
- `rurr-main/docs/compatibility/SEMANTICS.md:169-202`: exact sequence is a load selector; records have distinct position/status; missing initializer loads use defaults without copying requested sequence into default state; explicit fork source differs from target. App native identity/wire layout stays its own.
- **Halt caveat:** comments in `.../application/execution_options.rs:128-149` suggest generic before/after boundaries, but `.../application/session.rs:308-314` seeds the first action without testing halt-before; `:169-181,335-371,489-514` evaluates halt-before-next before halt-after-prior for ordinary run/iteration. Run output when before matches is pending action + no result; after is completed action + result. Streaming iteration uses the separate after-prior-first, current-session-commit rule in `:187-210`, called by `streaming/step_lifecycle.rs:237-251`; `tests/contract/application_streaming_contract/resumed_halts.rs:11-115` proves historical prior commits cannot suppress the first current-session action. WORKFLOW.md owns the exact App method mapping and same retained halt tuple in events and snapshot status; SPECIFICATIONS.md owns its existing DTO variant. Unknown selector/tag validation still occurs before any effect (`halt_controls.rs:14-24,55-90`; SEMANTICS.md:48-58).
- **Inputs caveat:** `.../application/session.rs:25-45,382-395,400-409` retains session inputs and passes them per advancement. A blanket “first action only” rule in the initial audit is not established by this source. Bindings/defaults/declared inputs must be tested with two successive actions reading the same runtime input. Runtime inputs still must not automatically become durable state or be copied into a fork.
- Streaming remains lazy; intermediate deltas are uncommitted, terminal completion commits (`.../application/api.rs:133-177`). History records committed boundary truth. A partial streaming notification is not a checkpoint or an independently resumable partial state.

## Tests-first acceptance set

Use public integration tests in existing `app-sdk/tests/workflow_execution.rs`, with focused new test targets only if necessary for a coherent domain. Pinned source/test/golden-derived App cases are mandatory and are not labeled runtime differential. An authorized installed oracle is optional additional evidence. No ZIP extraction/build, vendored dependency or extra Cargo workspace crate.

1. Serial A→B→C: initial action ordinal absent; step A returns seq0/resultA/stateA; step B returns seq1; step C seq2; exhaustion returns no step. Repeated control checkpoints during B do not skip user ordinals. Failure restores last committed state and preserves attempted position; explicit recovered failed-sequence selection follows pinned restart sequence semantics.
2. Iterate is lazy and exclusive: constructing then dropping invokes no action; first next validates selectors/inputs; second session/automatic execution receives Busy; observers remain usable; late caller drop cannot dispatch B after A's settled boundary. Same run reopened by another handle cannot bypass ownership.
3. Halt table: first-node before, before B, after A, before B+after A conflict precedence, unknown explicit node, unknown tag, duplicate selectors, multi-node tag, loop revisits, terminal frontier. Assert selected action/result/state and action-call count against rurr, not only paused status.
4. Input reuse/default/binding and no persistence: two actions consume the same session input as pinned rurr; reserved names fail before dispatch; changing durable initial state is independent; history and fork omit ephemeral tokens.
5. Broadcast input A + input B + sleeping C + agent D: all four become independently owned before any input resolution; resolving A preserves B/C/D; B may resolve first; duplicated A resolution returns identical applied evidence; conflicting payload fails without affecting B. Both two-agent branches actually overlap and read the same immutable base.
6. Barrier order: sibling completions shuffled in every order produce the same state/action ordinal ordering; zero reducer application while any required sibling remains pending; each staged result applied exactly once. JoinAll and JoinFirst cancellation preserve Unknown loser effects and terminalize only after cleanup.
7. History atomicity: crash/commit failure before immutable row write, after row staged, after head staged, after receipt staged, after commit but before reply. Reopen exposes either exact prior or exact next boundary, never orphan-visible history or a head pointing to absent history. Lost commit response reconciles one receipt without duplicate action execution.
8. History selection: page over >1 page, monotonic checkpoint identity with control-only rows, filter semantic action boundaries, exact action sequence, missing/invalid target, corrupt referenced predecessor, source definition revision mismatch and global history volume beyond one record bound. Concurrent append cannot shift a page captured to a committed head cutoff.
9. Late observer: wait/open/snapshot result after >1 second, App drain/shutdown and reopen; retained outputs/history remain available. Completing many runs reuses active capacity while retaining histories. Explicit terminal deletion races a result load/fork: transaction fences produce either successful copy/read or explicit NotFound/Conflict, never half-state. No receiver-pin family is needed under keep-until-delete default.
10. Fork: completed checkpoint resumes after saved action; safe failed boundary resumes its position; explicit restart uses configured entrypoint; overrides validated before new admission; fresh identity with source lineage; source state/history unchanged; deleting source after fork does not prevent target progress. Fork from old clean boundary of a currently Unknown source is permitted and explicit; forking the Unknown checkpoint itself fails without lower dispatch.
11. Crash at each external effect boundary: intent before dispatch, acceptance without stored lower identity, prompt result before contribution, notification resolve after lower success before app receipt, child admission after commit before activation. Reopen preserves accepted ownership and Unknown where evidence is insufficient; no blind retry, synthetic failure, dropped staged siblings or leaked capacity.
12. Streaming: action outputs arrive before terminal, user state/action ordinal remains prior until terminal; control-only history may advance; pre-commit-admission fail/drop/abort cannot create a completed action boundary, while post-admission observation loss is receipt-reconciled; terminal commit gives one retained result and one action ordinal. Explicit async finish/abort joins all admitted work.

Each slice's done criterion is: test introduced before production change, observed expected failure (or documented missing-proof test already passing), implementation green, independent subagent code review with all actionable findings resolved, owning specs/docs/examples updated, then the narrow crate gate. Final whole-crate and strict-live proof remains necessary; source inspection alone proves none of these runtime cases.
