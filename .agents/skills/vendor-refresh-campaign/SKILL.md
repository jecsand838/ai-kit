# Vendor Refresh Campaign

## Purpose

Run the top-level `ai-kit` vendor refresh workflow across one or more vendors.

## Trigger Boundary

Use this skill for a workspace-wide or crate-scoped vendor refresh campaign.
Do not use it for the single-vendor dossier flow generated by
`scripts/vendor_update.py`.

## Prerequisites

- Read [references/routing.md](references/routing.md) and
  [references/workflow.md](references/workflow.md).
- Confirm the tracked worktree is clean and record the starting branch.
- Confirm every in-scope crate whose vendor manifest runs a strict-live verify
  gate has a populated crate-local `strict-tests.env` file before execution.
  Today that means `agents-kit/strict-tests.env` and
  `storage-kit/strict-tests.env`.

## Workflow

1. Discover outdated vendors with `python3 scripts/vendor_update.py check --json`.
2. Preserve manifest order grouped by crate.
3. Run each queued vendor update sequentially with
   `python3 scripts/vendor_update.py update --crate <crate> --vendor <vendor> --git-mode current-branch`.
   When the user explicitly permits pre-existing failures but forbids broad
   backlog implementation, add `--completion-policy no-regression`; this still
   runs dossier planning and implementation, but blocks newly failing gates or
   diagnostics while recording unchanged baseline failures.
4. Rerun the final workspace and crate validation blocks for every crate in
   scope.
5. Stop on the first failed vendor update or final gate and leave artifacts
   intact for retry.

## Output Rules

- Execute the campaign unless the user explicitly asks for planning only.
- Report missing crate-local strict-live env files before starting updater runs.
- Do not push, open a PR, or create ad hoc branches unless the user explicitly
  asks.
- No-regression completion is not permission to skip prerequisites, weaken
  gates, or treat baseline failures as an implementation queue.
- Treat subagents as opt-in only.
