# app-sdk implementation, parity, and documentation audit

Audited 2026-09-13 at commit `9cec19c8eee6ca297e1e5e15de0a5dff3b5e61b9`, with a clean initial working tree, Rust/Cargo 1.94.1, and the checked-in app specifications. This report records observations and recommendations; it does not amend the specifications or authorize new public API shapes. Production code and existing tests were left unchanged. Temporary public-API probes were run separately from the existing suites.

**Verdict: app-sdk is substantially implemented, but it is not complete, does not have full feature or functional parity with the vendored rurr package, and is not ready to be certified against the requested production target.** The standard crate gate passes, but adversarial tests expose failures the existing suite misses. The downstream `docs/` directory exists but contains no pages.

There are two distinct completion problems. First, the current public contract deliberately excludes capabilities required for full rurr parity. Second, there are correctness defects and missing proof within the smaller contract already promised. Finishing the current allowlist alone cannot satisfy the expanded parity requirement. Amend the owning specifications as part of the completion work, while preserving the lower-crate composition boundaries.

The detailed evidence is in the [31-row pinned-rurr comparison](RURR_PARITY.md), [runtime review](RUNTIME.md), and [documentation/specification review](DOCUMENTATION.md). Those appendices distinguish normative app rules, normative lower-crate contracts, repository observations, pinned rurr observations, verified external facts, inferences, and unresolved gaps. A source finding is not represented as a runtime or strict-live test result.

**Scope and sources.** The audit covered all app production modules, the public inventory, all ten focused/umbrella specification documents, README, architecture guidance, scripts, four integration-test targets, Cargo boundaries, and the vendored archive. It reviewed workflow parsing/validation, evaluation/reducers, routing/joins, agent attempts, interactions, child/map execution, persistence, recovery, retention, workspace coordination, and lifecycle/task ownership. This is a comprehensive source and contract audit with targeted execution, not an exhaustive state-space or performance proof.

The rurr archive checksum is `5b5f20eb1d233467c600dc9dd249feaaa9046c5a303ae4e937040be5b6ecf25e`, with pinned commit `005bfe3ece631e64b06dac2d42ef84235f727a4f`. Exact members were read from the verified ZIP without extracting or running it. That snapshot identifies Burr v0.41.0 as its behavioral target. Its 16 workspace crates include much more than graph execution. Current official [Burr application](https://burr.apache.org/docs/concepts/state-machine/), [persistence](https://burr.apache.org/docs/concepts/state-persistence/), and [streaming](https://burr.apache.org/docs/concepts/streaming-actions/) documentation corroborate the capability distinctions. The documentation channel is unversioned; the latest official release was checked as [v0.43.0-incubating](https://github.com/apache/burr/releases/tag/v0.43.0-incubating) on the audit date. This does not change the pinned local parity baseline.

**What is already implemented.** The crate has a real engine, not just an API shell:

- `App → Workspace → Workflow → WorkflowRun`, strict versioned workflow parsing, canonical identifiers, and definition/child-inventory validation.
- Agent/state/input/child/map/join-all/join-first/sleep steps, typed expressions, first-match/broadcast routing, isolated staged state, and canonical barrier reduction.
- Checkpoint-zero admission, exact revision and generation fencing, mutation receipts, durable interaction/unknown states, cancellation, reopen/recovery, and bounded child admission.
- Workspace materialization, replacement/compensation/deletion, shared run ownership, and observed-versus-owned shutdown semantics.
- Direct `A: AgentBackend` and `CS: StateStoreBackend` composition. Each agent node contains a logical agent key; one workflow can select different configured agents at different nodes. Associated Workspace/Conversation types stay concrete and no `A: Clone` requirement is added.

These are implementation observations, with selected paths covered by tests. In particular, the existing two-agent live configuration contains no workflow definitions, so it does not prove two distinct agents executing different nodes in one workflow.

**Prioritized findings.** P1 items below block a production-completion claim. P2 items need specification/acceptance work or additional proof and are not all claims of broken implementation.

| ID | Priority and evidence | Finding and concrete impact | Recommended correction |
|---|---|---|---|
| A1 | P1; specification contradiction | The exact public ledger deletes fork/lineage, checkpoint selection, history/receivers, and tuning. Research explicitly excludes iteration, streaming, and tracking. | A3 | P1; reproduced | A lower `new_conversation` panic kills the task but leaves the run Running and the scheduler marked Driving. | A4 | P1; source-confirmed | A live attempt uses a single `OnceLock` notification and an already-Applied resolution cell. | A9 | P2 proof/spec gap | Missing direct coverage includes append-array/object-merge reducers, workflow retry-policy variants, successful structured output, multiple notifications, and real two-agent node handoff. **Parity means matching outcomes, not just listing similarly named features.** The most consequential differences are:

| rurr capability family | app-sdk status | Completion implication |
|---|---|---|
| General sync/async callable actions, action results separate from state, bound/default/optional runtime inputs | Closed step vocabulary; start input becomes durable checkpoint-zero state | Define ordinary action composition and transient input/output semantics. Do not force general computation through an Agent implementation merely to bypass a missing action seam. |
| Typed state, codecs, rich state operations and expressions | Bounded JSON plus a smaller typed expression/reducer vocabulary | Decide which behavior is portable and specify exact numeric, missing/null, invalid-type, mutation, and serialization semantics. |
| Numeric evaluation | App integer division gives `5/2 = 2`; rurr gives `2.5`. App `-5%2 = -1`; rurr gives `1` | Adopt or explicitly reject each semantic difference; matching operator names are not functional parity. |
| Step/iterate, halt-before/after, graph inspection/tags/visualization | No public equivalent | Add app-owned control/inspection contracts if full parity is retained. Polling snapshots can miss boundaries. |
| Partial-result/transactional streaming | No app stream; lower prompt returns terminal response | Separate workflow progress from agent payload streaming. The latter may require an Agent contract extension. Define buffering, backpressure, replay/drop, and commit semantics. |
| Historical checkpoint selection, fork/rewind, tracking | Explicitly excluded; current checkpoint and one predecessor only | Design lineage, definition/version compatibility, retention pins, and unknown-effect restrictions together. |
| Child/map execution | Meaningful common subset; fixed acyclic workflow inventory | Test nested-child depth bounds, recursion rejection, partial admission, indexed reduction, child failure/cancel/reopen. Dynamic task/executor/pipeline composition remains narrower than rurr. |
| Persistence backends | App consumes transactional StateStore; no direct rurr Redis/MongoDB adapters | Preserve storage ownership. Any backend requirement belongs to storage-sdk or caller implementations and must satisfy app transaction semantics. |
| Hooks, rich tracking artifacts, OTEL bridge, tracking server/UI/CLI, annotations/test extraction | Mostly absent or caller-owned | Full package parity needs explicit hosting/tooling scope decisions. Current root rules forbid new crates/substitute apps; do not silently fold these into the workflow runtime. Host-owned tracing export is appropriate but is not a tracking/history API. |

The [full matrix](RURR_PARITY.md) covers all 31 capability dimensions, ZIP evidence, macros/facades, telemetry, oracle/test tooling, and proposed ownership. Even a core-runtime-only reading of parity leaves action, input/result, execution-control, streaming, and history gaps. A whole-vendored-package reading additionally includes its server/UI/CLI and integrations. Preserving Rust representation differences is reasonable when behavior matches; silently omitting features is not full parity.

**Specifications that need extension.** Several documents are detailed about private mechanisms but light on caller-visible semantics and release criteria:

1. `SPECIFICATIONS.md` and `workflows/RESEARCH.md`: establish an exhaustive parity ledger, per-feature behavior, owner, exact pinned evidence, test, and acceptance criterion. Remove the contradiction between a full-parity product target and deliberate exclusions. Refresh the dated external research without moving the pinned baseline.
2. `workflows/WORKFLOW.md`: fully specify every expression/condition payload and type rule, integer/float behavior, division/modulo, missing versus null, interpolation, duplicate JSON keys, reducers including base-value participation and object collisions, route no-match, cycles, and join selection. Resolve the grammar inconsistency where “messages” are described as typed arrays but Sleep requires a string. Provide a hand-maintained JSON authoring schema and valid/invalid examples.
3. `WORKFLOW.md`, `CHECKPOINTS.md`, and `INTERACTIONS.md`: reconcile singleton versus simultaneous controls; define sibling progress and JoinFirst; specify repeated notifications, exact settlement replay, lost caller receipts, and capacity. Write an operation-by-operation deadline/panic/unknown matrix, including preparation and cleanup.
4. `WORKFLOW.md`: define retry applicability by step and failure phase, whether max_attempts includes the first attempt, what consumes budget, whether manual proven-safe Retry obeys it, and the recovery behavior of each timing policy. Accepting retry fields on every node does not prove those policies execute for every node.
5. `CHECKPOINTS.md`, `STATE_STORE.md`, and `APP.md`: define completed-result availability, retention values and units, history/fork if adopted, durable domain ownership, recovery guarantees, authoritative lower evidence, and supported process/generation model. Explain how to deploy changed workflow or Agent revisions when the App's durable inventory is immutable; define the supported rollout path without inventing implicit migrations.
6. `APP.md`, `WORKSPACE.md`, and `WORKFLOW.md`: document multiple agents per workflow, fresh conversation isolation, cross-node state handoff, static heterogeneous caller enums, lower failure semantics, and policy ownership. Current workspace lowering always selects full access/network enabled; decide whether that fixed policy fits the intended deployments rather than leaving callers to infer it from implementation.
7. `APP.md` and `OBSERVABILITY.md`: publish finite limits with scope, admission/capacity behavior, and error outcomes; define expected operational signals and correlation/redaction evidence. Task admission and simultaneous public-control requests also need explicit bounds. No throughput or recovery-time guarantee is established by source constants.
8. `workflows/TESTING.md`: add feature-by-feature deterministic, wire/lower, and strict-live evidence; multi-agent coverage; panic/hang/fault/receipt-loss/crash cases; docs/schema/example checks; and performance/recovery acceptance workloads. Three journey headings and an exact surface count are insufficient completion criteria.

**Completed docs folder acceptance.** The detailed [documentation review](DOCUMENTATION.md) provides content and tests for each page. At minimum deliver:

- `docs/README.md`, `QUICKSTART.md`, and `WORKFLOW_LANGUAGE.md`, plus `docs/schema/workflow-v1.schema.json`.
- `MULTI_AGENT_WORKFLOWS.md`, `STATE_AND_PARALLELISM.md`, and `INTERACTIONS_AND_CONTROLS.md`.
- `PERSISTENCE_AND_RECOVERY.md`, `LIFECYCLE_AND_OPERATIONS.md`, `OBSERVABILITY.md`, and `ERRORS_AND_TROUBLESHOOTING.md`.
- `STRICT_TESTING.md`, `RURR_PARITY.md`, and tested `docs/examples/*.json` definitions.

Include a runnable pure-state quickstart, two different agents on different nodes with state handoff, structured output, child/map/joins, repeated interactions, durable reopen, and shutdown. Explain that `wait()` returns actionable snapshots as well as terminal ones; the README's single wait followed by RejectActive does not handle an interactive workflow. Every guide must be discoverable, every JSON example parsed, deterministic examples executed, lower-service examples compiled and tied to real proof, and public methods documented with useful errors/fencing/drop/timeout guidance. Update the workspace documentation ledger. `missing-docs` success checks documentation presence, not completion.

**Loose-coupling decisions.** Retain caller-built Agent and app StateStore values, associated child backends, and per-node logical agent selection. Providers, tools, and managed knowledge remain owned below App; no lower credentials/configuration should be copied into workflow records. Under the current root contract, managed knowledge is private Agent behavior and there is no public KnowledgeBase handle to recreate. General action extensibility, token streaming, tracking/hosting, or new storage families may require coordinated amendments, but none justifies private lower access, backend inspection, erased Agent ingress, or a shared runtime framework.

**Recommended work order and exit criteria.**

1. Amend the parity/product contract and settle the blocking semantic decisions: action vocabulary, input/result separation, sibling controls, stream/history/fork, retention, and tooling ownership. Every pinned-rurr row must have a concrete outcome; a full-parity claim cannot contain undisclosed omissions.
2. Add regression tests, then fix deadline coverage, panic supervision, successive notification ownership, and workspace compensation fences. Prove every accepted effect ends in durable terminal truth or truthful Unknown, and every driver/control retains accountable ownership.
3. Implement the remaining adopted capability families in independent vertical changes, preserving each owning crate's boundary. Pair each change with its exact specification, documentation, and public behavioral proof.
4. Complete the language/reducer/retry matrix and real two-agent workflows, then crash/receipt-loss/cancellation/upgrade/retention cases. Add sustained load and recovery tests against explicit product targets before making production-scale claims.
5. Finish the docs tree and rustdoc using the supported implementation. Run all example/schema/link checks, exact crate gates and strict-live proof, then the documented workspace and locked clean-checkout release gates.

Until those criteria are met, describe app-sdk as an implemented but incomplete workflow engine with a narrower current contract and identified correctness defects. Do not describe the current crate as fully rurr-compatible or production-complete.
